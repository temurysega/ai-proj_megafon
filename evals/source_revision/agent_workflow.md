# Пересмотр после сверки платежей

## Воспроизведение

Из корня репозитория запустить расчёт и пересмотр. `--replay` извлекает используемые файлы CLI из Git-ревизии `6143ef4bfb78f4606554c3c8644bc6913c703307` в отдельный каталог `.cache/source-revision-*`. Каждый вызов `sf.py` запускается отдельным процессом в этой копии. Для одного расчёта флаг можно опустить. [agent_calc.py](agent_calc.py)

```powershell
python -X utf8 evals/source_revision/agent_calc.py --replay
```

В прогоне использованы только разделы вымышленного брифа. Копии `S01.md`, `S02.md`, `S03.md`, `S04.md` зарегистрированы как собственные материалы кейса с отметкой «Вымышленный учебный кейс». Идентификаторы CLI соответственно `S001`, `S002`, `S003`, `S004`. Ворота учебного проекта оставлены в `pending`. Проверка относится к минимальному стенду пересмотра на стадии `intake`. [brief.md](brief.md)

## До сверки и после получения акта

После `ingest S01.md` и `ingest S02.md` в `decisions.yaml` записано предварительное одобрение из S01 (`D1`, `active`). `C003` хранит наблюдаемый прирост записей в журнале платежей. `C004` воспроизводит использование этого прироста как оценки уникальных продлений до сверки. В `decision.md` раздел «Основание предварительного решения» ссылается на `C004`. Решение `D1` использует `C001` и `C004` и имеет триггер смены статуса `C004`. `sf decisions check` подтвердил структуру, чекпойнт сохранил задачу принять акт сверки.

Затем `ingest S03.md` вернул `S003`, после чего CLI показал следующие результаты. Ниже выдержки из фактического вывода, сокращены списки кандидатов и технические поля JSON.

```text
$ python sf.py revisit S003
C004 (score 1.49): Записи о продлении по журналу платежей дают оценку прироста уникальных продлений +6,64 п.п.

$ python sf.py claim retract C004 --reason "S03 выявил повторную обработку успешных платежей." --by C006
  "status": "superseded",
  "superseded_by": "C006",

$ python sf.py impact C004
  "claim": "C004",
  "dependent_claims": [],
      "file": "decision.md",
      "section": "Основание предварительного решения",
      "decision": "D1",
      "title": "Предварительно отправить всем",

$ python sf.py decisions due
🔁 D1: основание C004 стало «superseded» — пересмотреть решение (сверка уникальных платежей)

$ python sf.py checkpoint "C004 заменено C006 после S03, раздел и D1 требуют пересмотра." --next "Восстановить пересмотр: пересчитать экономику по S04, заменить рекомендацию и закрыть пометки."
Чекпойнт сохранён. Следующее действие: Восстановить пересмотр: пересчитать экономику по S04, заменить рекомендацию и закрыть пометки.
```

`revisit` предлагает кандидатов по текстовому сходству. После ручной сверки лишь `C004` заменено на `C006`, которое вычитает повторы по акту `S003`. `C003` остаётся активным историческим расчётом по журналу. `claim retract` сам записал пометки, а отдельный `impact` показал их адресатов.

## Продолжение по сохранённому состоянию

Следующий, отдельный вызов `status --json` прочитал из состояния следующий шаг, оба адресата пересмотра и записанный чекпойнт. Сокращённый фактический вывод приведён ниже.

```text
$ python sf.py status --json
  "next_action": "Восстановить пересмотр: пересчитать экономику по S04, заменить рекомендацию и закрыть пометки.",
  "stale": [
      "file": "decision.md",
      "section": "Основание предварительного решения",
      "file": "decisions.yaml",
      "section": "D1",
  "last_checkpoint": {
    "note": "C004 заменено C006 после S03, раздел и D1 требуют пересмотра."
```

По сохранённому шагу зарегистрирован S04, пересчитана экономика, записка заменена её обновлённым вариантом. В `decisions.yaml` прежний `D1` получил статус `reversed`, новый `D2` — `active`. `D2` хранит рекомендацию сохранить текущий процесс, этап проверки доступности и бюджета пилота в малых, метрики и триггеры. [agent.md](agent.md)
